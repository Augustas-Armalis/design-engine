# Introduction

Orientation chapter. It is almost entirely prose (marketing intro plus role definitions) and contains NO numeric design rules (no sizes, spacing, colours, contrast). Value for the engine: a shared vocabulary for the layers of design (UI / UX / CX), a list of what the UI role is responsible for, and the book's stance that UI is applied downstream of UX structure and must express the brand. Rules below are therefore process/scope rules, flagged as such. Printed page = PDF page - 1.

## 1. Core ideas

1. **UI is the visual and interactive layer; UX is the structure and experience beneath it.** UI = look, feel, interaction and presentation; closer to graphic design (colour, typography). UX = making the interaction between product and user enjoyable and usable; "analytical". (p.14, p.23)
2. **The two need each other.** UI without UX is "a painter throwing paint randomly at the canvas, hoping that'll look good"; UX without UI is "a sculpture with a frame that doesn't have anything to cover it" and so cannot define its purpose or be usable. (p.15 quote page)
3. **Skeleton and skin.** "A UX designer is the one who passes on the skeleton whereas, UI designer is the one who puts on the skin and cloth and dress that thing." The UI designer receives the needs and structure the UX designer produced and puts them into an attractive, aesthetically pleasing platform. (p.24, p.25)
4. **Scope nesting UI < UX < CX.** The p.13 diagram shows three concentric circles: UI innermost, UX around it, CX outermost. UI is tied to colour theory, typography, design patterns, interactivity and animations. UX adds desirable, valuable, findable, accessible, credible. CX adds attraction, awareness, advocacy, purchase, discovery, cultivation. (p.13)
5. **CX is broader than UX.** CX is the sum total of a customer's perceptions and feelings from every interaction with a brand's products and services, across the whole relationship (before purchase, active use, renewal or repeat purchase). UX is one part of CX. (p.28-30)
6. **UI must express the brand but is not branding design.** The UI designer implements the brand through the interface; example given: a Bed Bath & Beyond mobile site must express what Bed Bath & Beyond is about. (p.27-28)
7. **Principles first.** The book's advice for starting: learn the UI design principles before anything else; when UI is done well nothing is noticed, when done poorly users cannot get past it to use the product. (p.32-33)
8. **UX work is never finished.** A product has a lifespan; users, time and user base change opinions, so UX keeps monitoring ("like a mechanic after he leaves the car from the garage"). (p.19-20)

## 2. Rules

All rules here are process/scope guidance extracted from prose; none is numeric. Check is `visual` or `process` (a human/agent review step), not a measurement.

- **RULE** Treat visual design (colour patterns, typography, buttons, interactions) as the UI deliverable, and apply it to a structure and content plan that already exists. Do not invent information architecture while styling; if the structure is missing, define it first (sections, content priority, flows) and then style it.
  **Why** UI without UX structure is arbitrary decoration (p.15); the UI designer's job is to receive "all of the needs and structure" and present them attractively (p.24).
  **Applies to** all. **Check** process: a written section/content structure exists before visual styling begins. **Source** (p.15, p.24, p.25)

- **RULE** Make the interface express exactly what the company/product is, through the UI itself (the interface carries the brand: colour, type, tone), without turning the task into logo/brand-identity design.
  **Why** The UI designer "implements" the brand; they are not a branding designer but are closely tied to it.
  **Applies to** landing page | SaaS app UI. **Check** visual: a viewer can name the brand/product category from the UI with logo covered. **Source** (p.27, p.28)

- **RULE** Design for every screen size and resolution the product will be viewed on (the book names desktop, mobile device and an Xbox 360); the layout must "look good on each".
  **Why** Adapting to every screen size and resolution is part of the UI designer's responsibility.
  **Applies to** all. **Check** render at multiple viewports (e.g. desktop and mobile) and verify no overflow/broken layout. Specific breakpoints are not given in this chapter. **Source** (p.27)

- **RULE** Include inner animations, interactivity and prototyping in the UI scope, not only static visuals.
  **Why** "Nowadays it's a standard for UI designers to also think about inner animations, interactivity, prototyping."
  **Applies to** all. **Check** visual/process: interactive states (hover, press, transitions) are defined for interactive elements. **Source** (p.26-27)

- **RULE** Cover the full GUI element set: menus, tabs, widgets, input controls, navigational components and informational components.
  **Why** This is the book's enumerated list of what UI/UX designers design.
  **Applies to** SaaS app UI | forms | all. **Check** inventory of components present vs this list. **Source** (p.11)

- **RULE** Do competitive/market research (what is standard in the related market) before settling the look and feel, so the product "makes sense" in its category.
  **Why** Look and feel is the biggest UI element; the designer analyses market standards "to insure that the product make sense".
  **Applies to** landing page | SaaS app UI. **Check** process: reference set exists (and see examples/ layer). **Source** (p.26)

- **RULE** Put the user first in structure and content decisions ("always user comes first... ALWAYS"), and strategize how content is applied and received, since "content is king on the web".
  **Why** UX is a user-first discipline; content strategy is a large part of the UX role.
  **Applies to** all. **Check** process. **Source** (p.18)

- **RULE** Close the loop with the people who built and who use the product: incorporate customer feedback, usage metrics and usability findings; collaborate with developers so what ships looks and works as designed.
  **Why** The designer is responsible for the voice of the customer and for design-to-build fidelity.
  **Applies to** SaaS app UI | all. **Check** process. **Source** (p.12, p.19, p.27)

- **RULE** Make the purchase/engagement journey feel personal and appealing to the particular user (the book's example: a customer looking for shoes should find the experience equally appealing to engage with; the purchase "must be a delightful one").
  **Why** UX is about how the experience makes people feel, not only how it looks.
  **Applies to** landing page | e-commerce. **Check** visual/process (user-journey walkthrough). **Source** (p.20)

- **RULE** Use the UI/UX/CX lens as a checklist of qualities beyond appearance: UI (colour theory, typography, design patterns, interactivity and animations) inside UX (desirable, valuable, findable, accessible, credible) inside CX (attraction, awareness, advocacy, purchase, discovery, cultivation).
  **Why** Scope diagram, p.13.
  **Applies to** all. **Check** process: review a design against each ring. **Source** (p.13)

### Audit additions (audit 2026-10-15)

- **RULE** Illustrate design ideas as storyboards, process flows and sitemaps before high-fidelity screens, and gather/evaluate user requirements together with product managers and engineers.
  **Why** Listed as UI/UX role responsibilities; structure and flow are agreed before visual polish.
  **Applies to** all (process). **Check** process: a flow or sitemap artefact exists for multi-screen work. **Source** (p.11) (audit 2026-10-15)

- **RULE** Treat responsiveness problems as UX defects the designer must identify and troubleshoot, not as developer clean-up.
  **Why** "Identifying and troubleshooting UX problems (e.g., responsiveness)" is in the role list.
  **Applies to** all. **Check** render at mobile and desktop widths before hand-off. **Source** (p.12) (audit 2026-10-15)

- **RULE** Design the "no results" state of a search: keep the search field (with the query and a clear X) and the filter chips visible, and show an illustration, a short title ("Not Found") and one sentence that states the cause and the recovery ("Sorry, the keyword you entered cannot be found, please check again or search with another keyword") (read from the music-app figure).
  **Why** The empty state is a UI deliverable shown next to the results list and the action sheet; it tells the user what happened and what to do next.
  **Applies to** SaaS app UI | mobile. **Check** a zero-result query renders title + cause/recovery sentence, and the query and filters stay editable. **Source** (p.12) (audit 2026-10-15)

## 4. Dos and Don'ts

No UI good/bad comparisons in this chapter; the phone mockups (p.7, p.12) are decorative showcase screens, not instructional pairs. The only paired contrasts are conceptual:

| Do | Don't |
|---|---|
| Style a structure that already encodes user needs (skeleton then skin). | Style with no structure underneath: "painter throwing paint randomly" (p.15). |
| Give structure a visual layer that defines its purpose. | Leave a frame uncovered: "sculpture with a frame that doesn't have anything to cover it" (p.15). |
| Express the brand through the interface. | Treat the UI role as logo/brand design (p.27). |

## 5. Exceptions & judgement calls

- Source's own hedges: UI and UX have "some cross over, some gray areas"; the same person often wears both hats; development skill is helpful for UI designers "but not at all necessary" (p.14, p.23, p.24). Do not hard-code a strict handoff boundary.
- CX has "no right answer" for where it lives organisationally; the deciding factor should be proximity to actual clients so feedback arrives in real time (p.31). Not a rule for page design.
- Book's description of "UI" as "mostly digital" with a nod to non-digital interfaces (aircraft cockpits) (p.24). Engine scope remains web UI.
- Opinion, not rule: the "is UX design for you" checklist (problem solver, cognitive, analytical/psychological, wanting better UX than existing apps; p.21-22) is career advice. Note its Point 4 as printed ("more inclined to make something look interesting and look enticing versus be usable and feel-good, UX design could be for you") contradicts the rest of the chapter, which assigns "look enticing" to UI; likely an authoring error (see section 7).
- [engine note] "Skeleton then skin" is a useful default for the engine pipeline (structure and content plan first, visual system second), but in practice the visual direction often feeds back into structure; allow iteration rather than a one-way handoff.
- [engine note] The 'UI vs UX vs CX' circles are a conceptual aid. For a prompt-to-site engine, the practical use is: always produce (a) a content/section structure, (b) a visual system, (c) interactive states; and judge outputs on all three.
